Вход по почте и у каждого свои контакты

Приложение откроется только после входа. Человек вводит почту, получает письмо со ссылкой, нажимает — и он внутри. Паролей нет. Каждый видит и меняет только свои контакты, заметки и группы. Всё, что уже есть в базе, станет вашим.

1Коротко

  • Без входа любая страница ведёт на страницу входа: поле «Почта» и кнопка «Получить ссылку».
  • На почту приходит письмо «Вход в Личную CRM» с кнопкой «Войти». Ссылка срабатывает один раз и только 15 минут. Первый вход и есть регистрация, имя не спрашиваем.
  • Вход держится 30 дней с последнего захода на устройстве. В шапке — почта и «Выйти».
  • У каждого свои контакты, заметки и группы. Чужой контакт по прямой ссылке — «Контакт не найден», как будто его нет.
  • Все контакты, заметки и группы, которые уже есть в базе, при выкатке переходят к вам. Новый человек начинает с пустого списка.
  • Статус: спроектирована. Требования, дизайн и план готовы, код ещё не писали, отмечено 0 задач из 34. Автотесты (программы, которые сами проходят сценарий и сверяют результат) запланированы на 61 сценарий из 62: Vitest проверяет правила без браузера, e2e (автотест в настоящем браузере) — экраны и вход целиком. Один сценарий — настоящее письмо с сервера — проверяется руками после выкатки.

3Как это работает

Без входа — только страница входа

Любая страница приложения без входа ведёт на страницу входа. Без входа открываются только сама страница входа, «Ссылка устарела», проверка /health (её дёргает выкатка) и картинка для превью ссылки в мессенджерах.

Друг прислал вам адрес карточки, вы открыли его в браузере, где не входили → страница входа, данных контакта на ней нет.
Первый вход и есть регистрация

Отдельной формы нет, имя не спрашиваем. С новой почтой человек открыл ссылку — пользователь создан, человек внутри.

Почта: пробелы и регистр не важны

Пробелы по краям убираются, большие буквы становятся маленькими. Так везде: в запросе ссылки, в лимите писем, при входе.

« Anna@Example.COM » и «anna@example.com» — одна почта и один пользователь с одними и теми же контактами.
Ссылка: один раз, 15 минут, последняя отменяет прежние

Ссылка входит только при первом открытии и только 15 минут после запроса. Запросили новую — все прежние ссылки этой почты перестают работать. Ссылки других почт не трогаются.

Четвёртый запрос за любые 10 минут письмо не отправит. Лимит у каждой почты свой. Прежние ссылки при этом продолжают работать. Если письмо не ушло из-за сбоя, попытка не засчитывается.

Вход держится 30 дней с последнего захода

Каждый заход на устройстве продлевает вход ещё на 30 дней (с точностью до часа). Можно быть внутри с нескольких устройств сразу, у каждого свой срок. «Выйти» выходит только на этом устройстве.

Вошли 1 марта на ноутбуке и телефоне. Ноутбук открываете раз в неделю — он не просит входа. Телефон не открывали до 5 апреля — там страница входа. Нажали «Выйти» на ноутбуке — телефон это не затронет.
У каждого свои данные

Контакт и группа принадлежат тому, кто их создал. Заметки — владельцу контакта. Чужое для человека не существует: не видно в списке, поиске, фильтре, «Пора связаться», на странице «Группы». Прямой запрос к серверу с номером чужой записи ничего не меняет. Спрятанная кнопка — не защита: проверяет сервер.

У вас и у Бориса может быть по группе «Друзья» — это две разные группы. Борис откроет адрес вашей карточки → «Контакт не найден», ровно как для контакта, которого нет.
Куда уходят письма — решают настройки

Одна и та же сборка приложения работает везде, адрес почтового сервера берётся из настройки SMTP_URL в .env.

4Модель данных до и после

Модель данных — какие таблицы лежат в базе и какие в них поля. Фича добавляет пять таблиц для входа и одно поле «владелец» у контактов и групп.

Сейчас

Схему можно листать вбок.

Сейчас у записей нет владельца: все данные общие.

После

новоекак было

Схему можно листать вбок.

  • users — пользователи: одна строка на одну почту. Имя пустое — его не спрашиваем.
  • sessions — входы (сессия — вход, который браузер запоминает через cookie, маленький файл с ключом). У человека может быть несколько: ноутбук, телефон. «Выйти» удаляет только строку этого устройства.
  • verifications — ссылки из писем. В базе лежит не сама ссылка, а её хеш (зашифрованный отпечаток): даже по копии базы войти нельзя. Новая ссылка удаляет прежние той же почты.
  • sign_in_emails — по строке на каждое отправленное письмо. По ним считается лимит «3 письма за 10 минут».
  • accounts — служебная таблица библиотеки входа Better Auth. При входе по ссылке остаётся пустой.
  • contacts и groups получают поле user_id — владельца. Название группы теперь не повторяется только у одного человека.
  • notes и contact_groups не меняются: заметка принадлежит владельцу контакта, состав группы проверяется по контакту и группе.
  • Удалить пользователя, у которого есть контакты или группы, база не даст — случайно стереть чужие данные нельзя.

Как база находит свои и не находит чужие

К каждому запросу сервер сам добавляет условие «владелец — тот, кто вошёл». Номер пользователя никогда не берётся из формы или адреса — только из входа.

Миграция: одна, меняет уже существующие данные

Миграция — скрипт, который меняет устройство базы. Файл drizzle/0003_….sql, точное имя даст генератор. При выкатке сначала снимается бэкап, потом миграция запускается отдельным шагом до старта новой версии. Упадёт — новая версия не стартует, работает прежняя. Все шаги идут как одно целое: либо выполнятся все, либо ни один.

  1. Таблицы входа данные не меняет

    Создаёт пустые users, sessions, accounts, verifications и sign_in_emails.

  2. Поле «владелец» данные не меняет

    Добавляет пустое поле user_id контактам и группам.

  3. Назначить владельца меняет существующие данные

    Если в базе есть контакты или группы, берёт вашу почту из настройки OWNER_EMAIL в .env сервера, создаёт вас как пользователя и записывает вас владельцем каждого контакта и каждой группы. Остальные поля не трогаются, ничего не удаляется. Настройки нет, а данные есть — миграция падает, база остаётся как была. Пустой базе настройка не нужна.

  4. Правила данные не меняет

    Поле владельца становится обязательным и связывается с пользователем. Правило «название группы не повторяется» теперь действует внутри одного пользователя. Индексы (как оглавление в книге), чтобы база быстро находила записи владельца.

По правилам проекта агент покажет вам эту миграцию целиком до merge (задача 2.4). Ваша почта в код и в этот обзор не попадает: репозиторий публичный, почта есть только в .env.

Демо-данные (pnpm db:seed, заполняет только пустую базу) теперь создаются у пользователя с почтой из OWNER_EMAIL. Без этой настройки команда остановится с понятной ошибкой.

Откат — только вместе: версия и база

Прошлая версия приложения не знает про владельца и не сможет добавить контакт: база потребует user_id. Поэтому откатываются оба сразу: прошлая версия и бэкап базы, снятый первым шагом выкатки (файл before-deploy_…_SHA.dump). Как — в README, раздел «Вернуть и версию, и базу». Запускаете только вы, сам ничего не откатывается.

5Как проверить руками

Подготовка. Когда фича будет сделана:
  • В локальный .env добавлены четыре строки (агент скажет какие на шаге 1.4): секрет для входа, адрес приложения, адрес Mailpit и ваша почта OWNER_EMAIL.
  • docker compose up -d --wait — поднимет базу и Mailpit. Письма — на http://localhost:8025.
  • pnpm dev, приложение — http://localhost:3000.
  • Для двух пользователей: A — обычное окно браузера, B — окно инкогнито. Почты можно выдумывать: письма всё равно падают в Mailpit.
Пометки: e2e или Vitest — проверит автотест, руками для уверенности; только автотест — руками неудобно или невозможно (ждать 30 дней, запрос не из интерфейса); руками после выкатки — автотеста нет. Галочки на этой странице только для удобства и не сохраняются.

6Что агент решил сам

Продуктовые — стоит просмотреть

Вами решено: вход только по ссылке из письма, тексты из спеки, лимиты и сроки, письма через Resend и Mailpit, ваша почта — владелец существующих данных, автотест «два пользователя не видят данные друг друга», кнопка «Добавь первый контакт» как в спеке, страница входа без заголовка, тексты «Не получилось отправить письмо, попробуй ещё раз», «Получить новую ссылку» и «К списку контактов». Остальное ниже решено агентом.

  • Ваша почта хранится в настройке OWNER_EMAIL в .env, а не в коде: репозиторий публичный.
  • Адрес отправителя — noreply@mail.crm.pmcrm.site: вместо «моего домена» из спеки подставлен pmcrm.site.
  • Несуществующий контакт тоже показывает «Контакт не найден», а не «Такой страницы нет». Иначе по разнице текстов можно было бы понять, что чужой контакт есть. Из-за этого в двух старых e2e меняется ожидаемый текст.
  • Неудачная отправка письма не засчитывается в лимит. При сработавшем лимите прежние ссылки продолжают работать.
  • После «Ссылка отправлена» форма остаётся — можно запросить ещё раз.
  • Неверный адрес — текст остаётся в поле, как в других формах приложения.
  • Вошедший человек на странице входа сразу попадает в список.
  • После выхода «Назад» ведёт на страницу входа, а не к контактам.
  • 30 дней считаются с точностью до часа: срок продлевается не чаще раза в час.
  • Длинная почта в шапке на телефоне обрезается многоточием.
  • «Ссылка устарела» показывается при любой неудаче со ссылкой: использована, просрочена, отменена новой.

Технические — на экраны не влияют

  • Библиотека входа Better Auth 1.7.18 со способом «ссылка из письма». В базе хранится хеш ссылки, а не сама ссылка.
  • Встроенный в Better Auth адрес «запросить ссылку» закрыт снаружи: запрос идёт только через форму, где стоят проверка почты и лимит. Обойти их прямым запросом нельзя.
  • Лимит писем — своя таблица. Два одновременных запроса на одну почту идут по очереди, лимит не перескочить.
  • Владелец только у контактов и групп. У заметок и состава групп его нет: они проверяются через контакт и группу.
  • Удалить пользователя с контактами база не даст.
  • Каждая функция работы с данными требует номер пользователя и берёт его только из входа. Забыть проверку на одной странице нельзя.
  • Быстрая проверка «есть ли вход» на входе в приложение, настоящая — на каждой странице и в каждом действии.
  • Вход продлевается коротким запросом после загрузки страницы: при отрисовке страницы сервер не может обновить cookie.
  • Письма отправляет Nodemailer по адресу из SMTP_URL: на сервере это SMTP Resend (логин resend, пароль — ключ). Resend SDK не нужен.
  • Цвета в письме записаны прямо в письме: почтовые программы не понимают токены. Значения — те же, что у токенов.
  • Ни почта, ни ссылка не пишутся в журналы приложения. nginx и так пишет адреса без параметров, ключ ссылки туда не попадает.
  • Почту владельца миграция получает через настройку соединения с базой. Тестовые базы получают тестовую почту owner@example.com.
  • pnpm db:migrate запускает тот же скрипт миграций, что и сервер.
  • На сервере без новых строк в .env выкатка останавливается на первом шаге, до бэкапа и миграций.
  • Тесты: подменяются только функции Next «заголовки запроса» и «обнови страницы», база, Better Auth и Mailpit настоящие. Mailpit v1.33.0 добавляется в Docker и в CI.
  • Секрет для тестов на GitHub создаётся на каждый прогон, в репозитории его нет.
  • Телеметрия Better Auth (отправка статистики разработчикам библиотеки) выключена.

Предупреждение: почтовые сканеры

Некоторые почтовые сервисы сами открывают ссылки в письме, чтобы проверить их на вирусы. Одноразовая ссылка при этом сгорит, и человек увидит «Ссылка устарела». Если такое начнётся, понадобится страница-подтверждение с кнопкой — это отдельная доработка, сейчас её нет.
