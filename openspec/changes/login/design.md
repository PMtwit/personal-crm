# Design

## Context

Зачем это нужно - в proposal.md. Что должно работать - в `specs/user-auth/spec.md`, `specs/data-ownership/spec.md` и `specs/contact-groups/spec.md`.

Как сейчас:

- Входа нет. Любой, кто знает адрес, видит и меняет все данные.
- Данные читаются в `src/lib/data.ts`, меняются через server actions в `src/app/actions.ts`. Ни одна функция не знает, чей это контакт.
- Таблицы `contacts`, `notes`, `groups`, `contact_groups`. Уникальный индекс `groups_name_lower_idx` на `lower(name)` - на всю базу.
- Next.js 16.4 с `cacheComponents`. Файл `middleware` переименован в `proxy` (`src/proxy.ts`) и работает в Node.js. Страницы читают данные внутри `Suspense`.
- `notFound()` в карточке и на странице изменения показывает общую страницу «Такой страницы нет» (`src/app/not-found.tsx`). Два e2e ждут этот текст.
- Тесты: Vitest на своей базе `<name>_unit_test`, подменяется только `next/cache`. Playwright на базе `<name>_test`, `e2e/global-setup.ts` очищает таблицы и кладёт 30 контактов. Тесты кладут данные SQL-запросами прямо в базу.
- Миграции: `scripts/migrate.mts` в разовом контейнере на сервере. Локально `pnpm db:migrate` (`drizzle-kit migrate`). Тестовые базы мигрирует `prepareTestDatabase`. Обе тестовые базы живут между прогонами, и в них уже есть строки.
- На сервере `.env` с тремя строками Postgres. `deploy/compose.yaml` передаёт приложению только `DATABASE_URL`. nginx пишет в журнал путь без параметров адреса.
- Репозиторий на GitHub публичный.

Проверено по исходникам `better-auth@1.7.18`, последней стабильной на 06.11.2026:

- Плагин magic link хранит ссылку в таблице `verification`: в `identifier` строка `magic-link:<токен>`, в `value` JSON с почтой. Срок задаёт `expiresIn`. Ссылка расходуется атомарно на первом открытии, просроченная считается недействительной. Ошибка ведёт на `errorCallbackURL?error=...`.
- Старые ссылки при новом запросе плагин не отменяет. Лимита писем на почту в плагине нет: встроенный лимит Better Auth считает запросы по IP.
- `disabledPaths` закрывает путь только для запросов снаружи, вызов `auth.api.*` с сервера работает.
- Почту при создании пользователя Better Auth приводит к нижнему регистру, пробелы не убирает.
- Плагин `nextCookies` при отрисовке серверных компонентов не продлевает сессию: в этот момент cookie записать нельзя.
- Адаптер Drizzle умеет таблицы во множественном числе (`usePlural`) и сам сверяет схему.
- Телеметрия выключена по умолчанию.

## Goals / Non-Goals

**Goals:**

- Права проверяются у данных: каждая функция `src/lib/data.ts` принимает `userId` и фильтрует по нему. Забыть проверку на одной странице нельзя: без `userId` функция не вызовется.
- Одна сборка образа на компьютере, в CI и на сервере. Всё, что отличается, приходит из настроек.
- Выкатка не теряет данные. Без нужных настроек она останавливается раньше, чем что-то поменяет.
- Автотесты без моков базы и своего кода. Письма идут в настоящую заглушку Mailpit.

**Non-Goals:**

- Лимит запросов по IP на запрос ссылки - в спеке его нет. Встроенный лимит Better Auth остаётся только на открытие ссылки.
- Промежуточная страница «Нажмите, чтобы войти» против почтовых сканеров, которые сами открывают ссылки. См. риски.
- Очистка старых строк сессий и ссылок по расписанию.

## Decisions

### 1. Better Auth: магическая ссылка, свои правила вокруг неё

`src/lib/auth.ts`: `betterAuth` с адаптером Drizzle (`provider: "pg"`, `usePlural: true`), плагины `magicLink` и `nextCookies` (последним).

- `magicLink({ expiresIn: 900, storeToken: "hashed", sendMagicLink })`. Токен в базе хранится как хеш: утечка копии базы не даёт рабочих ссылок.
- `disabledPaths: ["/sign-in/magic-link"]`. Запросить ссылку можно только через наш server action, где стоят проверка почты и лимит. Второй двери в обход правил нет.
- `session: { expiresIn: 30 дней, updateAge: 1 час }`. Срок продлевается не чаще раза в час, поэтому 30 дней от последнего захода выдерживаются с точностью до часа.
- `baseURL` из `BETTER_AUTH_URL`, секрет из `BETTER_AUTH_SECRET`. `telemetry: { enabled: false }`. `advanced.ipAddress.ipAddressHeaders: ["x-forwarded-for"]`: nginx передаёт адрес клиента, без него встроенный лимит на открытие ссылки был бы один на всех.
- Маршрут `src/app/api/auth/[...all]/route.ts` через `toNextJsHandler`. Нужен для открытия ссылки и продления сессии.

Отказались:

- Свой вход без библиотеки: Better Auth в стеке в CLAUDE.md и в ограничениях спеки.
- Встроенный путь `/sign-in/magic-link` с хуком `before`: правила пришлось бы держать в двух местах, для формы и для прямого запроса.

### 2. Таблицы

Таблицы Better Auth в `src/db/schema.ts`, во множественном числе, как наши:

- `users`: `id text pk`, `name text not null` (пишем пустую строку, имя не спрашиваем), `email text not null unique`, `email_verified boolean`, `image text`, `created_at`, `updated_at`.
- `sessions`: `id`, `token unique`, `user_id → users on delete cascade`, `expires_at`, `ip_address`, `user_agent`, `created_at`, `updated_at`.
- `accounts` и `verifications` - по схеме Better Auth. `accounts` при входе по ссылке не заполняется, но адаптер ждёт эту таблицу.
- `sign_in_emails`: `id identity`, `email text not null`, `created_at timestamptz default now()`, индекс `(email, created_at)`. Одна строка - одно отправленное письмо. Нужна для лимита: строки ссылок удаляются при каждом новом запросе, считать по ним нельзя.

Владелец:

- `contacts.user_id text not null → users.id`, индекс `(user_id)`.
- `groups.user_id text not null → users.id`. Индекс `groups_name_lower_idx` заменяется на уникальный `groups_user_name_lower_idx (user_id, lower(name))`.
- Внешние ключи владельца без `cascade`: случайное удаление пользователя не сотрёт его контакты, база откажет.
- У `notes` и `contact_groups` колонки владельца нет: заметка принадлежит владельцу контакта, состав группы проверяется по контакту и группе. Второй источник правды мог бы разойтись с первым.

Отказались:

- `user_id` у заметок: лишняя копия, которую надо держать в согласии с контактом.
- Внешний ключ «контакт и группа одного владельца» через составные ключи: усложняет схему, а проверка в `setContactGroup` и тесты дают то же.

### 3. Данные: `userId` первым параметром

Все функции `src/lib/data.ts` получают `userId: string` первым параметром:

- Чтение: условие `contacts.user_id = userId` или `groups.user_id = userId`. Заметки и частота читаются через контакт этого пользователя.
- Изменение: то же условие в `where` у `update`/`delete`. Чужой номер даёт «не найдено» - тот же ответ, что и для несуществующего.
- `insertNote`, `setContactGroup`, `createGroupForContact` в транзакции проверяют, что контакт (и группа) принадлежат `userId`. Чужая группа для своего контакта - `group-not-found`.
- `createGroupForContact`: `insert ... on conflict do nothing` по новому индексу `(user_id, lower(name))`, поиск существующей - тоже в пределах `userId`.
- `renameGroup`: нарушение уникальности теперь значит «такая группа есть у этого пользователя».

`src/lib/session.ts`:

- `getCurrentUser()` - `auth.api.getSession({ headers: await headers() })`, обёрнута в React `cache()`: один запрос к базе на страницу, сколько бы блоков ни спрашивали.
- `requireUserId()` - без сессии `redirect("/login")`, иначе `user.id`.

Каждая страница и каждый server action берут `userId` только через `requireUserId()`. Номер пользователя из формы или адреса не принимается никогда.

### 4. Кто пускает на страницы

- `src/proxy.ts` делает быструю проверку: есть ли cookie сессии (`getSessionCookie` из `better-auth/cookies`). Нет - переход на `/login`. В базу proxy не ходит, как советует документация Next.js: он срабатывает и на предзагрузку ссылок.
- Пропускает без входа: `/login`, `/login/expired`, `/api/auth/*`, `/health`, `/_next/*`, `favicon.ico`, `opengraph-image*`. Превью ссылки в мессенджерах продолжает работать: страница входа берёт те же метаданные из `layout.tsx`.
- Настоящая проверка - в `requireUserId()` на каждой странице и в каждом действии. Cookie есть, а сессия истекла или удалена - тоже `/login`.
- `/login` при действующей сессии сразу ведёт на `/`.

### 5. Запрос ссылки: проверки, лимит и отмена старых ссылок

`src/lib/sign-in.ts`, `requestSignInLink(rawEmail, headers)`. Server action `requestSignInLinkAction` на странице входа только вызывает его и переводит ответ в текст.

1. `trim()` и `toLowerCase()`, потом `z.email()`. Неверно - `invalid-email`, дальше ничего не происходит.
2. Транзакция с `pg_advisory_xact_lock` по почте. Два одновременных запроса на одну почту идут по очереди, лимит не обойти.
3. Строк `sign_in_emails` по этой почте за 10 минут уже 3 - `rate-limited`. Старые ссылки при этом не трогаются, письмо не уходит.
4. Удалить из `verifications` все ссылки этой почты: `identifier like 'magic-link:%' and value::jsonb ->> 'email' = $email`.
5. `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers })`. Better Auth создаёт ссылку и вызывает `sendMagicLink` - тот отправляет письмо.
6. Письмо ушло - добавить строку в `sign_in_emails` и удалить строки этой почты старше 10 минут. Commit.
7. Письмо не ушло - исключение, транзакция откатывается: старые ссылки остаются, попытка не засчитана, ответ `send-failed`. В журнал пишется только «не отправилось письмо для входа» без почты и ссылки.

Ответы формы: `{ sentTo }` → «Ссылка для входа отправлена на <почта>»; `invalid-email` → «Проверь адрес почты» под полем; `rate-limited` → «Слишком часто, попробуй через несколько минут»; `send-failed` → «Не получилось отправить письмо, попробуй ещё раз». Есть ли такой пользователь, не проверяется вообще: ответ от этого не зависит.

Отказались:

- Лимит встроенным rate limiter Better Auth: он считает по IP, а спека требует по почте.
- Отмена старых ссылок внутри `sendMagicLink`: новая строка там уже создана, пришлось бы отличать её от старых по хешу токена.

### 6. Письма: Nodemailer, адрес сервера из настройки

`src/lib/mail.ts`:

- Транспорт `nodemailer.createTransport(process.env.SMTP_URL)`, создаётся при первой отправке. Нет `SMTP_URL` - понятная ошибка при отправке, а не при сборке образа.
- На компьютере `SMTP_URL=smtp://127.0.0.1:1025` (Mailpit). В CI так же, с адресом `localhost`. На сервере `smtps://resend:<ключ>@smtp.resend.com:2465`: Resend принимает SMTP, логин `resend`, пароль - ключ API. Порт 2465, а не 465: хостинг закрывает исходящие 25, 465 и 587 (проверено с сервера 2026-11-06). Код один и тот же.
- Отправитель `"Личная CRM" <noreply@mail.crm.pmcrm.site>` и тема «Вход в Личную CRM» - константы в коде, как требует спека. Mailpit принимает любой адрес отправителя, Resend - только с подтверждённого домена.
- Письмо в двух видах, HTML и текст: кнопка «Войти», «Ссылка работает 15 минут», «Если вы не запрашивали вход - просто проигнорируйте письмо». В HTML письма цвета пишутся прямо в стилях: почтовые программы не понимают переменные CSS. Цвета те же, что у токенов в `globals.css`, это единственное место вне токенов.

Отказались:

- Resend SDK: спека требует одну библиотеку Nodemailer для заглушки и для Resend.
- Переключатель «заглушка или Resend» в коде: решают настройки, а не код.

### 7. Экраны

- `src/app/login/page.tsx`: без заголовка, только поле «Почта» (`type="email"`, `autocomplete="email"`), кнопка «Получить ссылку». Клиентская форма на `useActionState`, как остальные формы. После отправки - «Ссылка для входа отправлена на <почта>» под кнопкой, форма остаётся: можно запросить ещё раз. Ошибка «Проверь адрес почты» - под полем, введённое остаётся. Оформление как у страницы «Такой страницы нет»: блок на градиенте, цвета и отступы через токены.
- `src/app/login/expired/page.tsx`: «Ссылка устарела, запроси новую» и кнопка «Получить новую ссылку» → `/login`.
- Шапка в `layout.tsx`: справа от логотипа `UserMenu` в `Suspense` с пустой заглушкой. Без входа его нет. С входом - почта (на телефоне обрезается многоточием, полностью видна в подсказке) и кнопка «Выйти» - форма с server action `signOutAction`: `auth.api.signOut({ headers })`, потом `redirect("/login")`. Cookie стирает `nextCookies`.
- Продление сессии: `UserMenu` после загрузки страницы один раз делает `fetch("/api/auth/get-session")`. Обработчик Better Auth при этом продлевает сессию, если её не продлевали больше часа, и сам пишет новую cookie. Клиентская библиотека Better Auth не нужна.
- `src/app/contacts/[id]/not-found.tsx`: «Контакт не найден» и кнопка «К списку контактов». Срабатывает для карточки и страницы изменения - и для чужого, и для несуществующего контакта. Общая «Такой страницы нет» остаётся для прочих неверных адресов.
- Пустой список нового пользователя - существующий экран из `src/components/contact-list.tsx`. Надпись «Пока нет ни одного контакта» прежняя, текст кнопки меняется на «Добавь первый контакт», как в спеке. Экран общий: эту кнопку увидит любой пользователь с пустым списком.

### 8. Миграция и почта владельца

`drizzle/0003_*.sql` создаёт `drizzle-kit generate`, потом её дописываем руками: сгенерированная `add column user_id text not null` упала бы на существующих строках. Порядок внутри одной транзакции миграций:

1. Создать `users`, `sessions`, `accounts`, `verifications`, `sign_in_emails`.
2. Добавить `contacts.user_id` и `groups.user_id` пока без `not null`.
3. Блок `DO`: если в `contacts` или `groups` есть строки, взять почту из `current_setting('app.owner_email', true)`. Пусто - `raise exception 'OWNER_EMAIL is not set: existing data needs an owner'`. Иначе создать пользователя с этой почтой (`lower(trim(...))`, `email_verified = true`, `name = ''`) и проставить его `id` всем контактам и группам.
4. `set not null`, внешние ключи, индексы, замена уникального индекса групп.

Миграция только добавляет: ни одна строка `contacts`, `notes`, `groups`, `contact_groups` не удаляется, их поля не меняются, кроме нового `user_id`.

Почта попадает в миграцию так: `scripts/migrate.mts` читает `OWNER_EMAIL` из окружения, проверяет её как почту, открывает одно соединение (не пул: настройка живёт, пока живёт соединение) и делает `select set_config('app.owner_email', $1, false)`, потом `migrate()`. Параметр запроса - экранировать ничего не надо. Это общая функция `runMigrations(connectionString, ownerEmail)` в `scripts/run-migrations.ts`, её же зовут `prepareTestDatabase` (тестовая почта `owner@example.com`) и тест миграций. `pnpm db:migrate` запускает `scripts/migrate.mts` через `tsx`: на компьютере и на сервере один путь.

Почта владельца в репозиторий не попадает: репозиторий публичный. Она есть только в `.env` на сервере и на компьютере.

Отказались:

- Почта прямо в миграции: видна всем на GitHub.
- «Кто первым вошёл, тот владелец»: друг может войти раньше.
- Отдельный скрипт «назначить владельца» после миграций: между миграцией и скриптом база жила бы с контактами без владельца, а `not null` на `user_id` пришлось бы ставить ещё одной миграцией.

### 9. Демо-данные

`scripts/seed.mts` требует `OWNER_EMAIL`. Находит пользователя с этой почтой или создаёт его, все демо-контакты и группы получают его `user_id`. Правило «только в пустую базу» прежнее.

### 10. Тесты

Vitest, на настоящей базе:

- Подменяются только `next/cache` (как сейчас) и `next/headers`. Помощник `signInAs(email)` создаёт настоящего пользователя и сессию через Better Auth и подставляет её cookie в заголовки запроса. Проверку сессии делает настоящий Better Auth.
- `src/lib/data.*.test.ts`: каждая функция с двумя пользователями - своё видно и меняется, чужое нет.
- `src/app/actions.*.test.ts`: действия с чужими номерами и без входа.
- `src/lib/sign-in.test.ts`: нормализация, неверная почта, лимит (строки с прошлым временем кладутся SQL), отмена старых ссылок, сбой отправки (неверный `SMTP_URL` в тесте). Письма уходят в Mailpit.
- `src/db/migrations.test.ts`: база на схеме `0002` с данными → все миграции с почтой владельца: число строк то же, всё у владельца. Без почты при данных - ошибка, база прежняя. Пустая база без почты - миграции проходят.

Playwright:

- `e2e/mailpit.ts`: последнее письмо на адрес через API Mailpit (`/api/v1/search`, `/api/v1/message/{id}`), ссылка из него. Чужие письма в заглушке тесту не мешают: ищем по получателю и времени.
- `e2e/global-setup.ts` очищает и таблицы входа, создаёт тестового владельца, 30 контактов кладёт ему.
- Проект `setup` в `playwright.config.ts`: `e2e/auth.setup.ts` входит под тестовым владельцем через форму и Mailpit, сохраняет состояние браузера в `e2e/.auth/` (в `.gitignore`). Существующие спеки работают с этим состоянием. Сценарий из `specs/01` остаётся отдельным файлом.
- `e2e/login.spec.ts` без сохранённого входа: главный сценарий спеки (A и B), письмо, повторная и просроченная ссылка (срок сдвигается SQL), отмена старых, лимит, сессия 30 дней (сроки в `sessions` сдвигаются SQL), выход на одном устройстве, `/health` без входа.
- В `main-scenario.spec.ts` два ожидания «Такой страницы нет» меняются на «Контакт не найден»: так требует новая спека.
- Секрет Better Auth для тестов не хранится в репозитории: `vitest.config.ts` и `playwright.config.ts` берут его из `.env` или CI, а если его нет - создают случайный на прогон. Поэтому ни тестам, ни CI отдельный секрет не нужен.

### 11. Окружения

- `compose.yaml`: сервис `mailpit` (`axllent/mailpit:v1.33.0`, последняя стабильная), порты `127.0.0.1:1025` (SMTP) и `127.0.0.1:8025` (страница в браузере).
- CI: сервис Mailpit в джобах Vitest и Playwright. `SMTP_URL` и секрет в CI не задаются: конфиги тестов подставляют `smtp://127.0.0.1:1025` и случайный секрет.
- `playwright.config.ts`: `BETTER_AUTH_URL=http://127.0.0.1:3100` для своего сервера.
- `Dockerfile`: при сборке временные значения `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL`, как сейчас у `DATABASE_URL`. Настоящие приходят из `.env` сервера при запуске. В образ копируется новый модуль миграций.
- `deploy/compose.yaml`: приложению и миграциям передаются `BETTER_AUTH_SECRET: ${BETTER_AUTH_SECRET:?...}`, `BETTER_AUTH_URL: https://app.pmcrm.site`, `SMTP_URL: ${SMTP_URL:?...}`, `OWNER_EMAIL: ${OWNER_EMAIL:?...}`. Нет строки в `.env` - `docker compose` падает на первой же команде `deploy.sh`, до бэкапа. Ничего не меняется, прежняя версия работает.
- `.env.example`: новые ключи без значений.
- Новые строки локального `.env`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=http://localhost:3000`, `SMTP_URL=smtp://127.0.0.1:1025`, `OWNER_EMAIL`. Пишет их владелец, агент только говорит, что добавить.

## Risks / Trade-offs

- [Почтовый сканер в ящике сам открывает ссылку, и она расходуется] → Человек увидит «Ссылка устарела» и запросит новую. Если это станет частым, отдельной правкой добавим страницу-подтверждение с кнопкой.
- [Хостинг закрывает исходящий SMTP] → Подтвердилось: с сервера закрыты 25, 465 и 587, открыты запасные порты Resend 2465 и 2587. Берём 2465: шифрование с первого байта, как на 465. До merge проверяем с сервера `nc -vz smtp.resend.com 2465`, после выкатки - настоящим письмом.
- [Письма попадают в спам] → Записи DNS от Resend (SPF, DKIM) для `mail.crm.pmcrm.site` ставит владелец до выкатки. Проверка - письмо на свою почту после выкатки.
- [Регистрация открыта всем, кто-то шлёт письма на чужие адреса] → Лимит 3 письма на адрес за 10 минут, письмо - только ссылка без данных. Лимита по IP в спеке нет. Если злоупотребления появятся, это отдельная фича.
- [Откат только приложения после выкатки] → Старая версия не знает про `user_id` и не сможет добавить контакт. Откат только парой: прошлая версия и бэкап базы, раздел README «Вернуть и версию, и базу». Бэкап снимается первым шагом выкатки.
- [Сессия продлевается только при загрузке страницы в браузере] → Это и есть «заход». Работа без JavaScript не продлевает вход, на это закладываться не нужно.
- [Почта и ссылка в журналах] → Ни почта, ни ссылка не пишутся в журнал приложения. nginx уже пишет путь без параметров адреса, токен в `?token=` в журнал не попадает.
- [Поведение `auth.api.signInMagicLink` при вызове из server action: проверка Origin] → Первым шагом реализации проверить на Vitest. Если Better Auth откажет, передавать заголовки запроса как есть.

## Migration Plan

До merge, руками владельца:

1. Аккаунт Resend, домен `mail.crm.pmcrm.site`, записи DNS из Resend у регистратора REG.RU. Дождаться «Verified».
2. Ключ API Resend с правом только на отправку.
3. В `.env` на сервере добавить `BETTER_AUTH_SECRET` (`openssl rand -hex 32`), `SMTP_URL` с ключом Resend и `OWNER_EMAIL`. Команды и точные строки агент даст в задачах.
4. Агент показывает миграцию `0003` до merge, как требует CLAUDE.md.

Выкатка - обычная, после merge: бэкап → миграции (владелец получает данные) → новое приложение → `/health`.

Проверка после выкатки, руками:

- https://app.pmcrm.site открывает страницу входа.
- Вход своей почтой: письмо пришло, видны все прежние контакты, заметки и группы.
- Вход другой почтой: пустой список, своих контактов владельца не видно.

Откат: только вместе - прошлая версия и бэкап `before-deploy_..._<прошлый SHA>.dump`, по README. Запускает владелец.
