# Личная CRM

Приложение, где я веду контакты людей, которых знаю лично: кто это, откуда знакомы, телефон и почта, о чём договорились. Идея и главный сценарий — в [specs/01-продуктовая-идея.md](specs/01-продуктовая-идея.md).

## Что нужно установить

- [Docker Desktop](https://www.docker.com/products/docker-desktop/) — в нём работает база данных
- Node.js 24 (LTS) и pnpm — ставятся через Homebrew:

  ```
  brew install node@24 pnpm
  ```

## Первый запуск базы данных

1. Создайте файл настроек из шаблона:

   ```
   cp .env.example .env
   ```

2. Откройте `.env` и заполните значения. Пароль можно сгенерировать командой `openssl rand -hex 24`. В `DATABASE_URL` подставьте те же имя пользователя, пароль и имя базы.

   Для входа в приложение добавьте ещё четыре строки:

   ```
   BETTER_AUTH_SECRET=длинная случайная строка
   BETTER_AUTH_URL=http://localhost:3000
   SMTP_URL=smtp://127.0.0.1:1025
   OWNER_EMAIL=ваша почта
   ```

   - `BETTER_AUTH_SECRET` — секрет, которым подписывается вход. Получить его можно командой `openssl rand -hex 32`
   - `SMTP_URL` — куда приложение отправляет письма со ссылкой для входа. На компьютере это почтовая заглушка Mailpit: письма никуда наружу не уходят
   - `OWNER_EMAIL` — ваша почта. Все контакты, которые уже есть в базе, достанутся пользователю с этой почтой. Она же нужна, чтобы наполнить пустую базу тестовыми данными. Почту знаете только вы: в git её класть нельзя, репозиторий открытый

3. Запустите базу и почтовую заглушку:

   ```
   docker compose up -d --wait
   ```

## Проверить, что база работает

```
docker compose ps
```

У `personal-crm-db-1` должен быть статус `(healthy)` и адрес `127.0.0.1:5432`. Рядом должна работать почтовая заглушка `personal-crm-mailpit-1`: её страница с письмами — http://localhost:8025.

Подключиться к базе и узнать её версию:

```
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select version();"'
```

## Остановить и запустить снова

- Остановить: `docker compose stop`
- Запустить: `docker compose up -d --wait`

База запускается сама вместе с Docker Desktop.

## Важно про данные

- Все контакты хранятся внутри Docker, в томе `personal-crm_pgdata`
- `docker compose down -v` **удаляет все данные без возможности восстановления**. Обычные `docker compose stop` и `docker compose down` данные не трогают
- База доступна только с этого компьютера — из локальной сети к ней подключиться нельзя
- `.env` с паролем не попадает в git. В git лежит только `.env.example` без значений

## Приложение

### Первый запуск

Все команды — в папке проекта, база должна быть запущена (см. выше).

1. Установить библиотеки:

   ```
   pnpm install
   ```

2. Создать таблицы в базе:

   ```
   pnpm db:migrate
   ```

   Если в базе уже есть контакты, все они станут контактами пользователя с почтой из `OWNER_EMAIL`. Без этой строки в `.env` миграция остановится с понятной ошибкой и ничего не изменит. В пустой базе почта не нужна.

3. Наполнить базу тестовыми данными — 1000 вымышленных контактов с заметками и пятью группами: Семья, Друзья, Знакомые, Дача, Аналитики (по желанию):

   ```
   pnpm db:seed
   ```

   Тестовые данные достаются пользователю с почтой из `OWNER_EMAIL`: если такого пользователя ещё нет, команда его создаёт. Команда срабатывает только на пустой базе. Если в ней уже есть хотя бы один контакт, она ничего не добавит и ничего не изменит. Почты у тестовых контактов — на служебных доменах `example.com`, `example.org`, `example.net`, поэтому письмо по ним никуда не уйдёт.

### Запустить

```
pnpm build
pnpm start
```

Откройте в браузере http://localhost:3000: это страница входа. Введите почту из `OWNER_EMAIL` и нажмите «Получить ссылку». Письмо придёт не в настоящий ящик, а в почтовую заглушку: откройте http://localhost:8025, найдите письмо «Вход в Личную CRM» и нажмите в нём «Войти». Остановить приложение — `Ctrl+C` в окне терминала, где оно запущено.

`pnpm build` нужен после каждого обновления кода. Если вы меняете код и хотите сразу видеть изменения, вместо этих двух команд запустите `pnpm dev`: так удобнее разрабатывать, но приложение работает медленнее.

Приложение открывается только на этом компьютере: из локальной сети, например с телефона, его не видно.

### Вход

- Без входа открывается только страница входа. Паролей нет: вводите почту, на неё приходит письмо со ссылкой, по ссылке вы в приложении. Первый вход с новой почтой сразу создаёт пользователя
- Ссылка работает один раз и 15 минут. Новая ссылка отменяет прежние. На одну почту уходит не больше 3 писем за 10 минут
- Вход держится 30 дней с последнего захода на этом устройстве. «Выйти» в шапке выходит только на этом устройстве
- У каждого пользователя свои контакты, заметки и группы. Чужой контакт по прямой ссылке показывает «Контакт не найден», как будто его нет
- Новый пользователь начинает с пустого списка

Чтобы проверить вдвоём на своём компьютере, второго человека откройте в окне инкогнито или в другом браузере, а письма смотрите в Mailpit (http://localhost:8025).

### Что умеет

- Главная страница — все контакты по алфавиту, с разбивкой по буквам
- Поиск по имени — список фильтруется во время набора. Регистр не важен, «ё» и «е» считаются одной буквой, слова можно вводить в любом порядке: «петров иван» найдёт «Иван Петров»
- «Добавить контакт» — имя (обязательно), кто это, откуда знакомы, телефон, почта
- Карточка контакта — все поля, кнопка «Изменить» и заметки. Новая заметка сохраняется кнопкой «Добавить заметку» или сочетанием ⌘ + Enter. Каждая заметка хранится отдельно, с датой и временем, новые — сверху

### Превью ссылки

Когда ссылку на приложение отправляют в мессенджер или соцсеть, показывается карточка: заголовок «Не теряйте людей, которых знаете лично», описание и картинка. Тексты и картинка те же, что у лендинга. Превью одинаковое для любой страницы приложения, имена контактов в него не попадают.

- Тексты — в `src/app/layout.tsx`, блок `openGraph`
- Картинка — `src/app/opengraph-image.png`, копия `public/og-image.png` из репозитория лендинга. Если картинку на лендинге перерисовали, скопируйте новую сюда под тем же именем
- Подпись к картинке для незрячих — `src/app/opengraph-image.alt.txt`

Мессенджеры запоминают превью. Если после выкатки видна старая карточка, в Telegram её можно обновить через бота `@WebpageBot`: отправьте ему ссылку.

### Проверить, что всё работает

Автотесты в браузере (e2e, папка `e2e/`) проходят:

- главный сценарий из спеки: открыть список → добавить контакт → найти по имени → дописать заметку → проверить, что всё сохранилось, в том числе при открытии в другом браузере (`main-scenario.spec.ts`)
- «Как часто общаться» и блок «Пора связаться» (`keep-in-touch.spec.ts`)
- дата рождения в форме контакта и в карточке, блок «Скоро день рождения» на главной (`birthdays.spec.ts`)
- переименование и удаление группы на странице «Группы»: новое название видно везде, а после удаления группы люди остаются на месте вместе с заметками (`groups.spec.ts`)
- вход по ссылке из письма, срок и одноразовость ссылки, лимит писем, вход на 30 дней, выход, и главное: два пользователя входят и не видят данные друг друга (`login.spec.ts`)

```
pnpm test:e2e
```

Тесты работают с отдельной базой `personal_crm_test` и запускают своё приложение на порту 3100, поэтому ваши контакты не трогают и запущенному приложению не мешают. Для тестов нужен установленный Google Chrome и запущенная почтовая заглушка (`docker compose up -d --wait`): тесты читают письма со ссылками из Mailpit. Письма тестов видны на http://localhost:8025. При каждом запуске тестовая база очищается и заполняется заново, тестовый владелец — `owner@example.com`.

### Автотесты Vitest

Быстрые проверки логики: правила названий, выборки из базы, действия приложения. Они лежат рядом с кодом, в файлах `*.test.ts` внутри `src/`.

```
pnpm test
```

Нужны запущенные Postgres и Mailpit в Docker (`docker compose up -d --wait`): тесты запроса ссылки читают отправленные письма из Mailpit. Тесты работают в отдельной базе `personal_crm_unit_test`: она создаётся сама при первом запуске, а перед каждым тестом очищается. Ваши контакты и база `personal_crm_test` для e2e не затрагиваются.

### Линтер, формат и типы

```
pnpm lint            # ошибки в коде (ESLint)
pnpm format          # выровнять оформление кода (Prettier): отступы, кавычки, переносы
pnpm format:check    # только проверить оформление, ничего не меняя
pnpm typecheck       # проверка типов TypeScript
```

Prettier не трогает тексты и спеки: `*.md`, `openspec/`, `specs/`, `landing-text/`. Список исключений — в `.prettierignore`.

## Проверки на GitHub (CI)

На каждый PR GitHub Actions запускает workflow «CI» (`.github/workflows/ci.yml`):

- «Lint, format, types» — `pnpm lint`, `pnpm format:check`, `pnpm typecheck`
- «Unit tests (Vitest)» — `pnpm test`
- «E2E tests (Playwright)» — `pnpm test:e2e`
- «Docker image build» — собирает образ приложения, но никуда его не отправляет
- «CI passed» — зелёная, только если зелёные все проверки выше

Базу и почтовую заглушку для тестов CI поднимает сам: временные Postgres и Mailpit в Docker, которые живут только во время проверки. Если e2e упали, записи упавших тестов лежат на странице проверки в разделе Artifacts (`playwright-traces`).

В `main` нельзя запушить напрямую: изменения попадают туда только через PR, и только когда «CI passed» зелёная. Правило действует и для владельца репозитория. Где посмотреть: Settings → Rules → Rulesets → «Protect main».

У PR включается автовлитие: PR вливается сам, как только CI позеленеет, и сразу запускается выкатка на тест-стенд. На прод — только кнопкой, см. «Выкатить на прод». Если CI красная, PR остаётся открытым: надо исправить причину и запушить в ту же ветку.

### Если что-то пошло не так

- На странице «Не получилось загрузить данные» — не запущена база. Откройте Docker Desktop и выполните `docker compose up -d --wait`
- `Port 3000 is in use` — приложение уже запущено в другом окне терминала. Откройте http://localhost:3000 или остановите то приложение

## Выкатка на сервер

На сервере два окружения:

- **Прод** — https://app.pmcrm.site, рабочее приложение
- **Тест-стенд** — https://test-app.pmcrm.site, закрыт паролем. На нём та же версия, что потом едет на прод, но своя база (копия данных прода) и свои ключи, см. «Тест-стенд»

После каждого merge в `main` новая версия сама выкатывается **только на тест-стенд**. На прод её выкатываете вы, кнопкой «Deploy prod» на GitHub, когда проверили тест-стенд. На прод попадает только версия, которая удачно выкатилась на тест-стенд.

В приложение входят по ссылке из письма, у каждого человека свои контакты (см. «Вход»). На сервере письма уходят по-настоящему, через Resend. Поисковикам страницы закрыты заголовком `noindex`.

### Как это устроено

1. После merge в `main` GitHub Actions (workflow «Deploy staging», `.github/workflows/deploy-staging.yml`) собирает образ приложения и кладёт его в GHCR. Тег образа — SHA коммита. Тот же workflow выкатывает этот образ на тест-стенд
2. Workflow «Deploy prod» (`.github/workflows/deploy-prod.yml`) запускаете только вы. Он берёт тот же образ, что на тест-стенде. GitHub помнит историю выкаток каждого окружения: «Deploy prod» по ней проверяет, что выкатка этой версии на тест-стенд была удачной. Нет — останавливается и ничего не меняет
3. Каждая выкатка копирует всё содержимое папки `deploy/` в папку своего окружения на сервере и запускает там `deploy.sh`. Новый скрипт в этой папке попадёт на сервер сам, менять workflow для этого не нужно
4. `deploy.sh` на сервере: на проде снимает бэкап базы (на тест-стенде бэкапа нет) → скачивает образ → разовым контейнером из этого образа применяет миграции → запускает новую версию → проверяет `/health`
5. Workflow ещё раз проверяет `/health` снаружи, через nginx: https://app.pmcrm.site/health или https://test-app.pmcrm.site/health
6. После удачной выкатки на прод удаляются старые образы — на сервере и в GHCR, см. «Чистка образов»

Если бэкап не снялся или миграции упали, новая версия не запускается, продолжает работать прежняя. Если проверка `/health` красная, выкатка считается упавшей. Сам ничего не откатывается: откат запускаете только вы (см. «Откатить прод»).

Две выкатки одного окружения одновременно не идут. На GitHub у каждого окружения своя очередь: вторая выкатка ждёт, пока закончится первая. На сервере у каждого окружения свой замок: если выкатка всё же началась во время другой выкатки, бэкапа или восстановления того же окружения, она сразу завершится с сообщением `Another deploy, restore, backup or database refresh is running`, ничего не меняя. Разные окружения друг другу не мешают.

До 15 ноября 2026 года был один workflow «Deploy», он выкатывал сразу на оба окружения. Его старые запуски не перезапускайте (Re-run): такой перезапуск выкатит на прод старыми скриптами, без проверки тест-стенда.

### Что где на сервере

| | Прод | Тест-стенд |
|---|---|---|
| Папка | `/srv/personal-crm` | `/srv/personal-crm-staging` |
| Проект docker compose | `prod` | `staging` |
| Контейнеры | `prod-app-1`, `prod-db-1` | `staging-app-1`, `staging-db-1` |
| Том с базой | `prod_pgdata` | `staging_pgdata` |
| Порт приложения (только 127.0.0.1) | 3000 | 3001 |
| Лимит памяти | нет | приложение 256 МБ, база 256 МБ |
| Бэкапы | `/srv/personal-crm/backups`: каждый день в 03:00 и перед каждой выкаткой | нет |
| Конфиг nginx | `app.pmcrm.site.conf` | `test-app.pmcrm.site.conf` |
| Сертификат | общий с лендингом: `pmcrm.site` | свой: `test-app.pmcrm.site` |

- В каждой папке: копия `deploy/` из репозитория и свой `.env`. Что в `deploy/`:
  - `compose.yaml` — контейнеры окружения
  - `deploy.sh` — выкатка и откат
  - `backup.sh` — бэкап базы прода, его каждый день запускает таймер
  - `restore.sh` — восстановление базы прода из бэкапа
  - `refresh-staging-db.sh` — свежая копия данных прода на тест-стенд
  - `common.sh` — общая часть скриптов
  - `nginx/` и `systemd/` — конфиги nginx и таймера бэкапа, ставятся на сервер вручную
  - `pick-prod-version.sh` и `clean-registry.sh` работают не на сервере, а на GitHub, в «Deploy prod». На сервер они копируются вместе с папкой, там не используются
- Файл `deploy-history` в папке окружения — список версий (SHA), которые удачно выкатились, по одной в строке. Последняя строка — текущая версия, строка перед ней — куда пойдёт откат
- Скрипты одни на оба окружения: адрес, порт и лимиты памяти каждого окружения записаны в `deploy/common.sh`. Скрипт, запущенный не из папки своего окружения, сразу останавливается и ничего не меняет
- Пользователь `deploy` нужен только для выкатки: он может запускать Docker, sudo у него нет. Его ключ лежит в секрете GitHub `DEPLOY_SSH_KEY`
- В каждом проекте docker compose: `db` — PostgreSQL, `app` — приложение, `migrate` — разовый контейнер для миграций
- nginx отдаёт приложение по адресам app.pmcrm.site и test-app.pmcrm.site. Конфиги лежат в `deploy/nginx/` и поставлены в `/etc/nginx/sites-available/` вручную, выкатка nginx не меняет: после правки файла его нужно поставить на сервер заново и перезагрузить nginx
- Сертификаты продлевает certbot сам и после продления перезагружает nginx
- В журнал nginx приложение пишет только путь страницы, без параметров адреса и без поля «откуда пришёл»: в параметрах бывают имена людей. Если приложение не отвечает, в журнале запросов будет код 502, а причину надо смотреть в журнале приложения

### .env на сервере

У каждого окружения свой файл, права 600: `/srv/personal-crm/.env` у прода, `/srv/personal-crm-staging/.env` у тест-стенда. В каждом шесть строк:

```
POSTGRES_USER=crm
POSTGRES_PASSWORD=пароль
POSTGRES_DB=crm
BETTER_AUTH_SECRET=длинная случайная строка
SMTP_URL=smtps://resend:КЛЮЧ_API@smtp.resend.com:2465
OWNER_EMAIL=ваша почта
```

Пароль можно сгенерировать командой `openssl rand -hex 24`. Адрес базы для приложения `compose.yaml` собирает из этих строк сам. Адрес сайта в `.env` не пишут: его задаёт скрипт по имени окружения.

У тест-стенда свои значения: другой пароль базы, другой `BETTER_AUTH_SECRET` и в `SMTP_URL` — свой ключ API Resend. `OWNER_EMAIL` тот же, что у прода.

- `BETTER_AUTH_SECRET` — секрет входа: `openssl rand -hex 32`. Если его поменять, все выйдут и войдут заново
- `SMTP_URL` — как приложение отправляет письма: через SMTP Resend, логин `resend`, пароль — ключ API Resend (права только на отправку). Порт 2465, а не обычный 465: хостинг закрывает обычные почтовые порты (25, 465, 587), а запасной порт Resend 2465 открыт. Шифрование то же
- `OWNER_EMAIL` — ваша почта. Все контакты, которые были в базе до входа, достаются пользователю с этой почтой. Нужна при каждой выкатке: если строки нет, выкатка останавливается на первом шаге, до бэкапа, и ничего не меняется
- Без любой из трёх новых строк выкатка остановится в самом начале с понятным сообщением, прежняя версия продолжит работать

Письма отправляются от имени `noreply@mail.crm.pmcrm.site`. Чтобы Resend их принимал, один раз настройте: аккаунт на resend.com → Domains → добавить домен `mail.crm.pmcrm.site` → записи DNS, которые покажет Resend, добавить у регистратора (REG.RU), дождаться статуса «Verified» → API Keys → ключ с правом только на отправку (Sending access). Проверить, что сервер достаёт до почтового сервиса: `ssh crm`, затем `nc -vz smtp.resend.com 2465` — ответ `succeeded`.

Создать или изменить файл:

```
ssh crm
sudo -u deploy bash -c 'umask 077 && nano /srv/personal-crm/.env'
```

Для тест-стенда — то же с `/srv/personal-crm-staging/.env`.

Пароль базы применяется только при самом первом запуске, когда база создаётся. Если потом поменять его только в `.env`, приложение не сможет подключиться: сначала пароль меняют в самой базе.

### Выкатить на прод

1. Влейте изменения в `main`: PR вливается сам, когда CI зелёная. Выкатка на тест-стенд запустится сама, её видно на GitHub: вкладка Actions → «Deploy staging». Идёт 3–5 минут
2. Проверьте новую версию на https://test-app.pmcrm.site
3. GitHub → вкладка Actions → слева «Deploy prod» → справа кнопка «Run workflow». В открывшемся окне:
   - «Use workflow from» — оставьте `main`. Запуск из другой ветки сразу остановится
   - «Commit SHA» — оставьте пустым
   - «Rollback» — не отмечайте
4. Нажмите зелёную кнопку «Run workflow». Через 3–5 минут откройте запуск: внизу страницы, в итогах (Summary), будет `Deployed. Prod runs ...` — SHA выкаченной версии, и `A rollback would bring back ...` — куда пойдёт откат

Что значат поля:

- **Commit SHA** пусто — выкатится последняя версия, которая удачно выкатилась на тест-стенд. Можно вписать SHA коммита, хватит первых 7 знаков. Это запасной путь, например чтобы выкатить конкретную версию. Если эта версия не выкатывалась на тест-стенд или её выкатка туда упала, запуск остановится с сообщением `has not passed the test stand` и ничего не изменит
- **Rollback** — откат, см. «Откатить прод». Поле SHA тогда не смотрится

Если выкатка упала, в итогах будет `Deploy ... failed`, а выше — шаг, на котором она остановилась, и его журнал. Сам ничего не откатывается.

На странице GitHub Environments → prod виден SHA ветки `main` на момент запуска, а не выкаченной версии: так GitHub устроен. Какая версия выкачена — в итогах запуска.

Перевыкатить тест-стенд: Actions → «Deploy staging» → нужный запуск → Re-run all jobs.

### Проверить, что работает

- https://app.pmcrm.site/health и https://test-app.pmcrm.site/health отвечают `{"status":"ok"}`
- Какая версия запущена и в каком состоянии: `ssh crm docker ps`, в колонке IMAGE видно SHA коммита
- Список версий прода, последняя строка — текущая: `ssh crm sudo -u deploy cat /srv/personal-crm/deploy-history`
- Логи приложения: `ssh crm TZ=Europe/Moscow journalctl -t prod-app-1 -n 100`, у тест-стенда — `staging-app-1`. Подробнее — в разделе «Логи»
- Сколько памяти занято и какой лимит: `ssh crm docker stats --no-stream`
- Если на сайте страница «Не получилось загрузить данные», откройте `/health` этого сайта. Ответ `database unreachable` значит, что приложение не достаёт до базы: проверьте `ssh crm docker ps`, у `prod-db-1` (или `staging-db-1`) должен быть статус `(healthy)`

### Логи

Все контейнеры прода и тест-стенда пишут логи в журнал сервера. Выкатка и откат заменяют контейнер, а его прошлые строки остаются в журнале: видно, что было и до выкатки.

Последние 100 строк приложения прода. У тест-стенда вместо `prod` пишите `staging`, так во всех командах ниже:

```
ssh crm TZ=Europe/Moscow journalctl -t prod-app-1 -n 100
```

Каждая строка начинается с даты и времени по Москве, имени сервера `kaza2` и контейнера. `TZ=Europe/Moscow` в начале команды нужен для московского времени, без него время будет по UTC, на 3 часа раньше.

- Следить вживую, новые строки появляются сразу; выход — Ctrl+C:
  `ssh -t crm TZ=Europe/Moscow journalctl -t prod-app-1 -f`
- За промежуток времени, время московское:
  `ssh crm 'TZ=Europe/Moscow journalctl -t prod-app-1 --since "2026-11-16 21:00" --until "2026-11-16 22:00"'`
- Только база: `-t prod-db-1` вместо `-t prod-app-1`
- Только миграции:
  `ssh crm TZ=Europe/Moscow journalctl COM_DOCKER_COMPOSE_PROJECT=prod COM_DOCKER_COMPOSE_SERVICE=migrate -n 50`
- Всё окружение сразу — приложение, база и миграции вперемешку, по времени. Удобно, когда разбираетесь с выкаткой:
  `ssh crm TZ=Europe/Moscow journalctl COM_DOCKER_COMPOSE_PROJECT=prod -n 200`

Сколько хранится:

- Журнал один на весь сервер, его размер ограничивает система: около 10% диска, сейчас примерно 2,4 ГБ. Когда журнал дорастает до предела, самые старые строки удаляются сами. Сколько он занимает сейчас: `ssh crm journalctl --disk-usage`
- Те же строки система копирует в `/var/log/syslog` и хранит там 4 недели
- `docker logs prod-app-1` тоже работает, но показывает только текущий контейнер, с последней выкатки

Чтобы читать журнал без sudo, пользователь `crmapp` состоит в группе `systemd-journal`. Это настроено один раз командой `sudo usermod -aG systemd-journal crmapp`, работает со следующего входа по ssh.

### Тест-стенд

https://test-app.pmcrm.site — проверить новую версию на копии настоящих данных, не трогая прод.

- **Пароль.** Сначала сайт спрашивает логин и пароль, потом приложение — почту для входа, как на проде. Без пароля открыт только `/health`: по нему GitHub проверяет выкатку
- **Вход.** Письма уходят по-настоящему, через Resend, но со своим ключом. Ссылка в письме ведёт на тест-стенд. Кука входа — только на test-app.pmcrm.site: вход на тест-стенде не действует на проде, и наоборот
- **Данные.** Копия последнего бэкапа прода: контакты, заметки, группы, пользователи. Сессии, ссылки входа и счётчик писем из копии удаляются: на тест-стенд входят заново, по письму. Изменения на тест-стенде на прод не попадают
- **Других внешних служб** у приложения нет, кроме почты

Задать или поменять логин и пароль стенда. Пароль команда спросит сама, дважды, на экран он не выводится. Вместо `ЛОГИН` впишите любое имя латиницей:

```
ssh crm
printf 'ЛОГИН:%s\n' "$(openssl passwd -6)" | sudo tee /etc/nginx/test-app.pmcrm.site.htpasswd >/dev/null
sudo chown root:www-data /etc/nginx/test-app.pmcrm.site.htpasswd
sudo chmod 640 /etc/nginx/test-app.pmcrm.site.htpasswd
```

Новый пароль действует сразу, nginx перезагружать не нужно. Пока файла с паролем нет, на тест-стенд не пускает никого: любой логин и пароль отвергаются.

**Обновить данные тест-стенда** — если они испортились или устарели. Скрипт берёт самый свежий бэкап прода, удаляет базу тест-стенда, загружает бэкап, применяет миграции версии, которая стоит на тест-стенде, удаляет сессии и запускает приложение той же версии. Прод не меняется, его бэкап только читается. Ничего не спрашивает, тест-стенд на минуту недоступен:

```
ssh crm
sudo -u deploy /srv/personal-crm-staging/refresh-staging-db.sh
```

Бэкап прода снимается каждый день в 03:00. Если нужна совсем свежая копия, сначала снимите бэкап вручную: `sudo -u deploy /srv/personal-crm/backup.sh`.

**Откатить тест-стенд** на версию до текущей, повторный откат — ещё на шаг назад:

```
ssh crm
sudo -u deploy /srv/personal-crm-staging/deploy.sh staging rollback
```

GitHub про такой откат не знает: «Deploy prod» с пустым полем SHA по-прежнему возьмёт последнюю удачную выкатку на тест-стенд, то есть версию, с которой вы откатились.

### Откатить прод

Откат запускаете только вы: GitHub → Actions → «Deploy prod» → «Run workflow» → отметьте **Rollback** → «Run workflow». Поле SHA при этом не смотрится, тест-стенд не проверяется.

- **Куда.** На версию, которая стояла до текущей: список версий прода помнит сервер. Второй откат подряд — ещё на шаг назад: были версии A → B → C, первый откат вернёт B, второй — A. Если последняя выкатка упала уже после запуска новой версии, откат вернёт последнюю удачную
- **Итоги.** В итогах запуска будет `Rolled back. Prod runs ...` — версия, которая теперь работает, и куда пойдёт следующий откат. Если откатываться некуда, запуск остановится с сообщением `No earlier prod version to roll back to` и ничего не изменит
- **Бэкап.** Перед откатом скрипт тоже снимает бэкап базы
- **Образ.** Откат на версию до текущей работает всегда: её образ хранится на сервере. Образ версии старше, если ему больше двух недель, с сервера уже удалён: тогда он скачается из GHCR, если он среди 10 последних сборок
- **Вперёд.** Вернуться на новую версию: «Deploy prod» с пустым полем SHA

Миграции при откате не отменяются. Если новая версия меняла таблицы, старая может с ними не заработать: перед таким откатом проверьте, какие миграции были в новой версии. Чтобы вернуть и версию, и таблицы, смотрите «Вернуть и версию, и базу».

### Бэкапы базы

У прода два вида бэкапов:

- **Ежедневный** — каждый день в 03:00 по Москве, файл `daily_...`. Его запускает таймер на сервере. Если сервер в 03:00 был выключен, бэкап снимется, когда сервер включится
- **Перед выкаткой** — первым шагом каждой выкатки на прод, в том числе отката, файл `before-deploy_...`. Не снялся — выкатка останавливается, ничего больше не меняется

У тест-стенда бэкапов нет: его данные — копия прода.

- Где лежат: `/srv/personal-crm/backups`. Внутри личные данные, поэтому читать их может только пользователь `deploy`
- Имя файла: `daily_2026-11-16_03-00-01_SHA.dump` или `before-deploy_2026-11-04_21-30-05_SHA.dump` — московское время и версия приложения, которая стояла в этот момент. Если приложения ещё не было, вместо SHA будет `none`
- Сколько хранится: по 7 последних каждого вида. Лишние `before-deploy_...` удаляются после удачной выкатки, лишние `daily_...` — после удачного ежедневного бэкапа. Упавшие выкатка или бэкап ничего не удаляют
- Копии `before-restore_...` снимает восстановление. Сами они не удаляются: когда станут не нужны, удалите их вручную
- Бэкапы лежат на том же сервере, что и база. От неудачной выкатки они защищают, от потери самого сервера — нет

Посмотреть список:

```
ssh crm
sudo -u deploy ls -lh /srv/personal-crm/backups
```

Снять бэкап вручную, когда нужно. Если в этот момент идёт выкатка или восстановление, скрипт подождёт до 30 минут. В конце напишет `Saved` и путь к файлу:

```
ssh crm
sudo -u deploy /srv/personal-crm/backup.sh
```

Проверить, что ежедневный бэкап работает:

```
ssh crm
systemctl list-timers personal-crm-backup.timer
journalctl -u personal-crm-backup.service -n 20
```

Первая команда показывает следующий запуск (NEXT) и прошлый (LAST). Время в ней по UTC: 03:00 по Москве — это 00:00 UTC. Вторая показывает журнал последних бэкапов, удачный заканчивается строкой `Saved ...`. Если ежедневный бэкап упал, он об этом никому не сообщает: видно только в журнале и по списку файлов.

Таймер ставится один раз. Если файлы в `deploy/systemd/` поменялись, после выкатки на прод его ставят заново, теми же командами:

```
ssh crm
sudo install -m 644 /srv/personal-crm/systemd/personal-crm-backup.service /srv/personal-crm/systemd/personal-crm-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now personal-crm-backup.timer
```

### Восстановить базу из бэкапа

Запускаете только вы. База заменяется целиком: всё, что появилось в ней после этого бэкапа, из базы исчезнет и останется только в копии `before-restore_...`.

```
ssh crm
sudo -u deploy ls -lh /srv/personal-crm/backups
sudo -u deploy /srv/personal-crm/restore.sh /srv/personal-crm/backups/ИМЯ_ФАЙЛА
```

Скрипт проверит файл и покажет, что собирается сделать. Сообщения в нём на английском:

- `Backup file` и `Size and time` — какой файл загрузится, его размер и время
- `Database to replace` — какая база будет заменена
- `App version now` — версия приложения сейчас, она не изменится
- `App version of backup` — версия из имени бэкапа
- `WARNING` — эти версии разные, и приложение может не заработать с таблицами из бэкапа. Если сомневаетесь, отмените и смотрите «Вернуть и версию, и базу»

Чтобы продолжить, введите `yes` и нажмите Enter. Любой другой ответ отменяет восстановление, ничего не меняется.

Дальше скрипт снимает копию текущей базы `before-restore_...`, останавливает приложение, удаляет базу, создаёт её заново, загружает бэкап и запускает приложение той же версии. На это время сайт недоступен. Миграции скрипт не запускает.

Проверить результат: https://app.pmcrm.site/health отвечает `{"status":"ok"}`, на сайте видны данные из бэкапа, в `ssh crm docker ps` та же версия, что была.

`restore.sh` — только для прода. Из папки тест-стенда он не запустится и подскажет `refresh-staging-db.sh`.

Выкатка прода и восстановление не идут одновременно. Если во время восстановления началась выкатка прода, она сразу упадёт с сообщением `Another deploy, restore, backup or database refresh is running in prod`, ничего не меняя: когда закончите, запустите «Deploy prod» заново. Если идёт выкатка прода, скрипт восстановления так же сразу завершится: дождитесь её конца. Ежедневный бэкап, если начнётся во время восстановления, подождёт до 30 минут. Выкатка тест-стенда восстановлению не мешает.

**Если восстановление упало.** Скрипт напишет `RESTORE FAILED`, на каком шаге это случилось и где лежит копия базы. Сам он ничего не откатывает. Если упала загрузка бэкапа, приложение остаётся выключенным. Чтобы вернуть базу, какой она была, запустите восстановление ещё раз с копией `before-restore_...`.

### Вернуть и версию, и базу

Нужно, когда новая версия меняла таблицы и прежняя версия с ними не работает. Сначала версия, потом база:

1. Откатите прод кнопкой, см. «Откатить прод». Откат первым шагом снимет свежий бэкап — копию базы на случай, если передумаете
2. Найдите бэкап `before-deploy_...`, который сняла выкатка отменяемой версии: в его имени SHA той версии, на которую вы только что откатились. Восстановите из него базу:

```
ssh crm
sudo -u deploy ls -lh /srv/personal-crm/backups
sudo -u deploy /srv/personal-crm/restore.sh /srv/personal-crm/backups/ИМЯ_ФАЙЛА
```

Версия в имени бэкапа и версия приложения совпадут, предупреждения `WARNING` не будет.

Нужна версия старше предыдущей — впишите SHA из имени бэкапа в поле «Commit SHA» запуска «Deploy prod». Так можно выкатить только версию, которая удачно выкатывалась на тест-стенд, то есть сделанную не раньше 14 ноября 2026 года.

Откат сам снимает новый бэкап, поэтому самый старый из 7 может удалиться. Если нужен именно он, сначала сохраните его копию вне папки `backups`.

### Чистка образов

После каждой удачной выкатки на прод, в том числе отката:

- **На сервере** удаляются образы приложения старше двух недель, кроме двух последних версий прода (текущей и той, куда пойдёт откат) и текущей версии тест-стенда. Выкатка тест-стенда сама ничего не чистит: если долго не выкатывать прод, образы копятся. Свободное место: `ssh crm df -h /`
- **В GHCR** остаются 10 последних сборок, старые удаляет задание «Clean up GHCR» в том же запуске «Deploy prod». Если оно красное, прод уже выкачен: упала только чистка

### Тестовые данные на сервере

1000 вымышленных контактов с заметками и группами, как у `pnpm db:seed`. Достаются пользователю с почтой из `OWNER_EMAIL`. Срабатывает только на пустой базе:

```
ssh crm
sudo -u deploy bash -c 'cd /srv/personal-crm && . ./common.sh && use_environment prod && APP_TAG=$(tail -n 1 deploy-history) compose run --rm -T migrate node scripts/seed.mts'
```
